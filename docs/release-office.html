      Schedule

      Who sits where

      Rooms

      101

      Owner’s office

      The owner · person

      • Chooses the work. He moves a ticket from To Do, through Elaboration, to In Progress.
      • Answers what the developer cannot settle, and takes any cross-team discussion or change to a protected path himself.
      • Hears from the manager when a ticket is blocked and when it reaches staging.

      102

      Manager’s desk

      Agent · the hub

      • Keeps the list of tickets given to the developer and where each one stands.
      • Carries every message between the developer and the reviewer, and can ask either for a report at any time.
      • Checks the merge request itself: approved, pipeline passed, marked ready.
      • Moves the ticket to Reviewed, assigns the merge to the maintainer, and starts the next ticket. On the merge it moves the ticket to Deployed to Staging.
      • Answers the owner at any time: who is working, what is with the reviewer, and how many of the office’s own merge requests are waiting for the maintainer.
      • Writes no code and reviews none.

      103

      Developer

      Agent · on the owner’s token for now

      • Gathers the requirements, writes the code, runs the tests and the checks the ticket names.
      • Opens the merge request and moves the ticket to Completed.
      • Fixes review threads and replies on each one. It never resolves, approves or merges.
      • Reports progress, completion and blockers to the manager, and to no one else.
      • Its session stays open until the merge, so a late comment finds it with the full context.

      103

      Co-author

      Agent · clean context, posts nothing

      • Sits at the developer’s desk with no memory of how the change was written.
      • Reviews the local change against the ticket before the merge request opens.
      • Hands its findings to the developer. It posts nothing to GitLab.

      104

      Reviewer

      Agent · separate clean session

      • A separate session with a clean context. Local for now, so it works on the owner’s token.
      • Acts only when the manager passes it a message.
      • Looks closely and makes sure the merge request maps exactly to the Jira ticket. Every requirement and every decision must match.
      • Posts each mismatch or finding as a thread.
      • Checks the fixes, resolves the threads it has verified, then approves.
      • Never pushes code and never merges.

      105

      Merge desk

      The maintainer · person

      • Merges the approved request into staging once the manager assigns it to him.
      • May comment or push back first. The manager passes that to the developer.
      • The merge is his decision. No agent can make it.

      Fixtures

      A

      Sprint board

      Jira · Sprint 1

      • Seven columns, from To Do to Done.
      • The owner’s move to In Progress is what starts the office.
      • The developer moves the ticket to Completed. The manager moves it to Reviewed and to Deployed to Staging.

      B

      MR hatch

      GitLab · the merge request

      • Set in the solid wall between the two rooms.
      • The developer pushes code in from one side.
      • The reviewer writes threads, resolves them and approves from the other.
      • It is the only thing both rooms touch.

      C

      Test bench

      Tests · checks · pipeline

      • The project’s own tests.
      • The wider checks the ticket names, such as a smoke run.
      • The pipeline runs the checks again on the merge request.

      D

      Ticket file

      Jira · the ticket itself

      • The reviewer reads the ticket for itself and checks the merge request against it, requirement by requirement and decision by decision.
      • The owner’s answers to the developer’s questions are written here too.

      E

      Protected paths

      Locked

      • The paths the repo marks as protected are outside this office.
      • When a ticket needs a change there, the owner makes it himself.

      F

      Staging door

      Way out

      • Merged work leaves here. Merged into staging is deployed to staging.
      • QA on staging then catches any drift in columns or records.
      • Done comes later, with the production release.

      Sheet notes

      General notes

      1. The owner starts every ticket. The office works only on tickets he has moved to In Progress.
      2. Every message crosses the manager’s desk. No door joins the developer’s room to the reviewer’s.
      3. The merge request is the one thing both rooms touch. The developer pushes into it and the reviewer writes on it.
      4. Local for now. Every role runs on the owner’s machine with his own GitLab and Jira tokens. A separate reviewer token is the later step.
      5. The reviewer approves only when the merge request maps exactly to the Jira ticket, with every requirement and every decision matching.
      6. The reviewer’s approval counts toward the merge. The maintainer, a person, performs it.
      7. The manager checks three things itself before asking for a merge: approved, pipeline passed, marked ready. GitLab itself refuses a merge while any thread is open.
      8. Anyone may comment on the merge request. The manager passes each comment to the developer.
      9. The developer’s session stays open until the merge. The next ticket starts as soon as one is handed over for merge.
      10. Protected paths stay locked, and a change there is the owner’s own work.
      11. Merged into staging is deployed to staging. QA on staging then checks for drift in columns and records.
      12. A local control page will start the office and show who is working. Its backend runs the Claude CLI, and it lists only the office’s own merge requests.
